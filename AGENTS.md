# Project agent memory

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

- Add durable project-specific notes here as they are discovered through real work.
- Build: `swift build` / `swift build -c release`. Test: `swift test`. No Xcode project - pure SwiftPM.
- `Sources/PinchosCore` is UI-free; `Sources/pinchos` is the AppKit wiring layer. Both are covered by `swift test` (`Tests/PinchosCoreTests` and `Tests/pinchosTests` respectively). See [README.md#architecture](README.md#architecture) for the current module responsibilities.
- `ItemConfig` (`Sources/PinchosCore/ItemConfig.swift`) is the single command-item model for `[item.<id>]` tables; its only public fields are the canonical item keys documented in README. `MenuRowConfig` is the ordered generic row model for static values, cached values, actions, combined value/actions, and separators. The parser rejects groups and every deferred key with source path and line diagnostics. Item icons use one `ItemIconSource` (`.file` / `.symbol`), and an unavailable runtime symbol keeps the item valid while rendering text-only with a doctor/diagnostics note. Visual target stays 16×16 with no size key. See `StatusItemIconRenderer` and README icon/`symbol` docs.
- TOMLKit's `TOMLTable` iterates keys alphabetically (backed by `std::map` in the vendored `toml++`), not in file declaration order - see `ConfigParser.declaredItemOrder`, which line-scans for `[item.*]` headers separately from TOMLKit's actual parse/validation. If item ordering ever seems wrong after a TOMLKit upgrade, this is the first place to check.
- Measure idle memory with `footprint <pid>` (`phys_footprint` line), not `ps`'s RSS column - `ps` counts dyld shared-cache pages mapped read-only across every process on the system, inflating a small Swift/AppKit binary's reported RSS by ~3x over its actual physical footprint.
- Config resolution: `$XDG_CONFIG_HOME/pinchos/pinchos.toml` if that env var is set and non-empty, else `~/.config/pinchos/pinchos.toml`. See `Sources/pinchos/ConfigLocation.swift`.
- GUI config reload (`AppDelegate` + `ConfigWatcher`) never reads or parses the config on `@MainActor`: both route through `ConfigLoadCoordinator` (`Sources/pinchos/ConfigLoadCoordinator.swift`), an actor that runs the file read/TOML parse off-actor, serializes at most one load at a time (TOMLKit concurrency safety is unverified), coalesces bursts of reload requests into a single pending slot, and discards any result superseded by a newer request (success or failure) before handing it back to `@MainActor`.
- Manual QA evidence lives in `docs/manual-qa/`. The 0.1.0 pass used marker-file timestamps instead of screenshots because this environment has no human available to grant the one-time Screen Recording/Accessibility permission `screencapture`/Accessibility APIs require - if a future session runs with a real logged-in GUI session and that permission already granted, prefer real screenshots.
- Retained command output (`Sources/PinchosCore/TailByteBuffer.swift`) is a ring buffer with amortized O(1) append, not a `Data` recopy - and every stdout/stderr collector process-wide draws from one shared `OutputMemoryBudget` (default 8MiB, see `CommandExecution.swift`/README "Output memory budget"). `CommandRunner` has an internal (non-public) initializer accepting a custom `OutputMemoryBudget` for tests that need to prove aggregate-budget behavior without mutating the shared singleton other concurrently-running tests rely on.
- `SignalIntegrationTests.pinchosExecutable()` prefers `.build/.../release/pinchos` over the debug binary when both exist. `swift test` only rebuilds the debug target, so a release binary built earlier in a session (or on a stale checkout/rebase) silently goes stale and those tests exercise old code with no compiler warning. If a `SignalIntegrationTests` failure looks unrelated to your change, rerun `swift build -c release` before trusting the result. This repo also has many concurrent agents sharing `main` and the `.codex/worktrees/issue-N/pinchos` naming convention - re-fetch/rebase onto latest `origin/main` immediately before finalizing a branch, since a mid-session merge can silently reintroduce stale code that git's line-based merge doesn't flag as a conflict.
- Reload/removal/reorder-rebuild/shutdown cancel every affected primary or menu-row runner across items concurrently under one shared, monotonic deadline via `settleConcurrently`/`LifecycleDeadline` (`Sources/pinchos/LifecycleSettlement.swift`), not sequentially. The deadline instant is computed once per operation and threaded through every item/runner instead of being restarted per item. See `ManagedItem.prepareUpdate`/`prepareRemoval` and `StatusItemController.apply`/`rebuild`/`shutdownNow`.
- One application-scoped `CommandScheduler` (`Sources/PinchosCore/CommandScheduler.swift`) bounds every scheduled/manual refresh and menu-row action process-wide and owns the single shared deadline timer; there is no per-item `DispatchSourceTimer` or public scheduler configuration. `StatusItemController` constructs one instance and passes it to every `ManagedItem` via `DefaultManagedItemFactory`; `ManagedItem` acquires a permit before a session and releases it exactly once on that session's final settlement (see `ManagedItem.requestRefresh`/`ManagedItem.invokeMenuRow`). See README for the fixed internal policy and diagnostics.
- Every `CommandRunner` execution spawns a supervisor shell (`ProcessSessionSpawner.swift`) that the app talks to over a raw control pipe (`SupervisorProcessSession.send`, `ProcessSession.swift`). That pipe's write end has `F_SETNOSIGPIPE` set at creation - without it, the supervisor dying before a planned `send()` (killed with its process group, or from resource exhaustion under heavy concurrent load) delivers SIGPIPE with default disposition and kills the *entire host process* instantly, not just that write. This was the root cause of an intermittent `swift test` "Exited with unexpected signal code 13" CI crash inside `CommandExecutionTests`. Any new raw `write()`/`send()` to a pipe or socket this process doesn't fully control needs the same treatment (or `MSG_NOSIGNAL` for sockets).

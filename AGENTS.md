# Project agent memory

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

- Add durable project-specific notes here as they are discovered through real work.
- Build: `swift build` / `swift build -c release`. Test: `swift test`. No Xcode project - pure SwiftPM.
- `Sources/PinchosCore` is UI-free; `Sources/pinchos` is the AppKit wiring layer. Both are covered by `swift test` (`Tests/PinchosCoreTests` and `Tests/pinchosTests` respectively). See [README.md#architecture](README.md#architecture) for the current module responsibilities.
- `ItemConfig` (`Sources/PinchosCore/ItemConfig.swift`) is a sum type — `.command(CommandItemConfig)` / `.group(GroupItemConfig)` — not one flat struct; adding a third module kind means a new case, not new optional fields on an existing one. `PinchosConfig.hiddenMemberNames`/`.topLevelItems` implement the group visibility policy (a group member never gets its own top-level `NSStatusItem`); `StatusItemController` computes `isTopLevel` per item from these and threads it through `ManagedItemFactory.make` so `ManagedItem`/`ManagedGroupItem` skip `NSStatusItem` creation entirely for hidden members rather than creating-then-hiding one. See README "Groups" for the full schema/policy and `ConfigDiffTests`/`GroupConfigTests`/`GroupStatusItemTests` for the behavior this depends on (visibility flips force a remove+add "recreate", never an in-place update, because `NSStatusItem` has no such transition). Command and group items share one `ItemIconSource` (`.file` / `.symbol`); the parser rejects setting both `symbol` and `icon` (item/key/line). An unavailable runtime symbol keeps the item valid and renders text-only with a doctor/diagnostics note rather than rejecting reload. Visual target stays 16×16 with no size key. See `StatusItemIconRenderer` and README icon/`symbol` docs.
- TOMLKit's `TOMLTable` iterates keys alphabetically (backed by `std::map` in the vendored `toml++`), not in file declaration order - see `ConfigParser.declaredItemOrder`, which line-scans for `[item.*]` headers separately from TOMLKit's actual parse/validation. If item ordering ever seems wrong after a TOMLKit upgrade, this is the first place to check.
- Measure idle memory with `footprint <pid>` (`phys_footprint` line), not `ps`'s RSS column - `ps` counts dyld shared-cache pages mapped read-only across every process on the system, inflating a small Swift/AppKit binary's reported RSS by ~3x over its actual physical footprint.
- Config resolution: `$XDG_CONFIG_HOME/pinchos/pinchos.toml` if that env var is set and non-empty, else `~/.config/pinchos/pinchos.toml`. See `Sources/pinchos/ConfigLocation.swift`.
- GUI config reload (`AppDelegate` + `ConfigWatcher`) never reads or parses the config on `@MainActor`: both route through `ConfigLoadCoordinator` (`Sources/pinchos/ConfigLoadCoordinator.swift`), an actor that runs the file read/TOML parse off-actor, serializes at most one load at a time (TOMLKit concurrency safety is unverified), coalesces bursts of reload requests into a single pending slot, and discards any result superseded by a newer request (success or failure) before handing it back to `@MainActor`.
- Manual QA evidence lives in `docs/manual-qa/`. The v1 pass used marker-file timestamps instead of screenshots because this environment has no human available to grant the one-time Screen Recording/Accessibility permission `screencapture`/Accessibility APIs require - if a future session runs with a real logged-in GUI session and that permission already granted, prefer real screenshots.
- Retained command output (`Sources/PinchosCore/TailByteBuffer.swift`) is a ring buffer with amortized O(1) append, not a `Data` recopy - and every stdout/stderr collector process-wide draws from one shared `OutputMemoryBudget` (default 8MiB, see `CommandExecution.swift`/README "Output memory budget"). `CommandRunner` has an internal (non-public) initializer accepting a custom `OutputMemoryBudget` for tests that need to prove aggregate-budget behavior without mutating the shared singleton other concurrently-running tests rely on.
- `SignalIntegrationTests.pinchosExecutable()` prefers `.build/.../release/pinchos` over the debug binary when both exist. `swift test` only rebuilds the debug target, so a release binary built earlier in a session (or on a stale checkout/rebase) silently goes stale and those tests exercise old code with no compiler warning. If a `SignalIntegrationTests` failure looks unrelated to your change, rerun `swift build -c release` before trusting the result. This repo also has many concurrent agents sharing `main` and the `.codex/worktrees/issue-N/pinchos` naming convention - re-fetch/rebase onto latest `origin/main` immediately before finalizing a branch, since a mid-session merge can silently reintroduce stale code that git's line-based merge doesn't flag as a conflict.
- Reload/removal/reorder-rebuild/shutdown cancel every affected runner (primary/click/action, across items) concurrently under one shared, monotonic deadline via `settleConcurrently`/`LifecycleDeadline` (`Sources/pinchos/LifecycleSettlement.swift`), not sequentially - see `ManagedItem.prepareUpdate`/`prepareRemoval` and `StatusItemController.apply`/`rebuild`/`shutdownNow`. The deadline instant is computed once per operation and threaded through every item/runner instead of being restarted per item.
- One application-scoped `CommandScheduler` (`Sources/PinchosCore/CommandScheduler.swift`) bounds every scheduled/manual refresh and command action process-wide and owns the single shared deadline timer; there is no per-item `DispatchSourceTimer` anymore. `StatusItemController` constructs one instance and passes it to every `ManagedItem` via `DefaultManagedItemFactory`; `ManagedItem` acquires a permit before a session and releases it exactly once on that session's final settlement (see `ManagedItem.requestRefresh`/`handleClick`/`invokeAction`). See README "Scheduler" for the policy (default limit, `[scheduler] max_active_sessions` override, fairness/coalescing contract, diagnostics).
- Configured info rows (`[[item.<name>.info]]`) are read-only menu status lines: `StatusItemController.addCommandContent` spawns a fresh `CommandRunner` per row at every menu open and renders `<title>: <output>` (or `–` on failure). Their `run` feels like an action but there is no persistent runner, no diff-driven re-application beyond `CommandItemConfig` equality, and every row costs one extra process + (for quota items) one API call per open — keep them to cheap reads (see the rate-limit note on the live config). Documented in README/skill; parser mirrors `parseActions` minus `refresh`.
- `output = "json-v1"` items are parsed by `StructuredOutputParser` (`Sources/PinchosCore/StructuredOutput.swift`); see README "Versioned structured output" for the schema/error contract. In `ManagedItem.renderPresentation`'s `.error` case (`Sources/pinchos/ManagedItem.swift:~704`), `state = "error"` from a *successful* parse (exit 0, no output diagnostic) is not a genuine failure — it must keep the script's real text and apply error styling only, never fall back to `commandConfig.errorText`/`on_error`. `isGenuineFailure` (checks `snapshot.outputDiagnostic` and `terminalReason`) gates that distinction; see `StructuredOutputLifecycleTests` for the regression coverage.
- Every `CommandRunner` execution spawns a supervisor shell (`ProcessSessionSpawner.swift`) that the app talks to over a raw control pipe (`SupervisorProcessSession.send`, `ProcessSession.swift`). That pipe's write end has `F_SETNOSIGPIPE` set at creation - without it, the supervisor dying before a planned `send()` (killed with its process group, or from resource exhaustion under heavy concurrent load) delivers SIGPIPE with default disposition and kills the *entire host process* instantly, not just that write. This was the root cause of an intermittent `swift test` "Exited with unexpected signal code 13" CI crash inside `CommandExecutionTests`. Any new raw `write()`/`send()` to a pipe or socket this process doesn't fully control needs the same treatment (or `MSG_NOSIGNAL` for sockets).
- Event-driven item refreshes are owned by `ItemTriggerCoordinator` (`Sources/pinchos/ItemTriggerObservation.swift`), which incrementally retains or stops per-item observers for `startup`, `wake`, `network-change`, and normalized watched paths; callbacks debounce by source and call the existing `ManagedItem.requestRefresh` gate. OS-specific wake/network/file observation stays behind `ItemTriggerObserverFactory`, with fake observers covering debounce, reload, and removal lifecycle in `Tests/pinchosTests/ItemTriggerObservationTests.swift`.

- Item failure and recovery notifications live across `Sources/PinchosCore/ItemNotification.swift`, `Sources/pinchos/ItemNotificationSink.swift`, and `ManagedItem`: `notify_on`/`notify_cooldown` are opt-in terminal-transition policy, stale and successful structured `state = "error"` are not command failures, and the shared system sink resolves `UNUserNotificationCenter` lazily so headless tests and unconfigured items do not touch notification services. See `NotificationTests` and `NotificationLifecycleTests` for transition, cooldown, bounded-context, and unchanged-identity coverage.

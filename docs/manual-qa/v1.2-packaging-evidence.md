# v1.2 packaging - manual QA evidence

Evidence for [issue #15](https://github.com/douglasjarquin/pinchos/issues/15), gathered against an **unsigned** `Pinchos.app` produced by `scripts/package-app.sh` in this same headless-agent environment (see the "known limitation" note in `docs/manual-qa/v1-evidence.md` - no human is available to grant the one-time GUI permissions real notarization/Gatekeeper/screenshot verification would otherwise use). Signing and notarization themselves are exercised only by `.github/workflows/release.yml` against real Apple credentials, which do not exist in this repository yet (see `docs/releasing.md`).

## 4. Unsigned by default (expected, pre-signing state)

```sh
$ codesign -dv dist/Pinchos.app
CodeDirectory v=20400 size=17376 flags=0x20002(adhoc,linker-signed) hashes=540+0 location=embedded
Signature=adhoc
TeamIdentifier=not set
Sealed Resources=none

$ spctl --assess --type execute --verbose=4 dist/Pinchos.app
dist/Pinchos.app: code has no resources but signature indicates they must be present
```

`adhoc` (the linker's default, not a real identity) and a Gatekeeper rejection are the expected, correct result for `scripts/package-app.sh`'s output - this is exactly why it's a structure-smoke tool, not the distribution path. `scripts/ci/codesign-app.sh` in `.github/workflows/release.yml` is what actually applies a Developer ID signature; that step cannot be exercised in this environment because the signing secrets in `docs/releasing.md` do not exist here.

## 5. CLI entry point inside the bundle, outside a dev shell

Simulated a Finder/non-Terminal launch by running the bundled binary directly with `env -i` (empty environment, so no inherited dev `PATH`, shell profile, or `SWIFTPM`/Xcode variables), only `HOME`, `USER`, and a scratch `XDG_CONFIG_HOME` set:

```sh
$ env -i HOME="$HOME" USER="$USER" XDG_CONFIG_HOME="$SCRATCH" \
    dist/Pinchos.app/Contents/MacOS/pinchos init
Created example config: $SCRATCH/pinchos/pinchos.toml

$ env -i HOME="$HOME" USER="$USER" XDG_CONFIG_HOME="$SCRATCH" \
    dist/Pinchos.app/Contents/MacOS/pinchos doctor
Pinchos doctor
Config path: $SCRATCH/pinchos/pinchos.toml
[PASS] config: readable and parsed
[FAIL] execution environment: PATH is missing or empty
[PASS] execution environment: HOME is available
[PASS] item.clock.shell: /bin/sh
[PASS] item.clock.working_directory: inherits Pinchos working directory
[PASS] item.clock.icon: not configured
[PASS] item.clock.env: inherits process environment
[FAIL] item.clock.run: command 'date' is unavailable in the configured shell environment
[FAIL] launch at login: app registration is unavailable
Doctor found 3 problems.
```

This confirms `doctor` correctly diagnoses a genuinely PATH-less environment (`date` needs `PATH` resolution and none is set here) rather than silently passing or crashing - the actual failure mode a real Finder launch could hit if a user's configured `run` command relies on `PATH` instead of an absolute path. Rerunning with an absolute-path command in the same PATH-less environment succeeds end-to-end:

```sh
$ env -i HOME="$HOME" USER="$USER" XDG_CONFIG_HOME="$SCRATCH" \
    dist/Pinchos.app/Contents/MacOS/pinchos run clock   # run = "/bin/date +%H:%M"
23:09
```

("launch at login: app registration is unavailable" is expected here too: `SMAppService` requires the process to have actually been launched through Launch Services as that bundle, which directly exec'ing the inner Mach-O from a shell does not simulate - only a real `open dist/Pinchos.app` from a logged-in GUI session exercises that path, which this headless environment cannot grant permissions for, matching the same limitation `docs/manual-qa/v1-evidence.md` already documents for v1.)

## Discovered nuance: `NSHomeDirectory()` ignores an overridden `HOME` environment variable

An earlier attempt at this evidence pass set a *different* scratch `HOME` (instead of `XDG_CONFIG_HOME`) to simulate "no `XDG_CONFIG_HOME`, default to `$HOME/.config`" per the issue's acceptance criteria, expecting `ConfigLocation.resolve()` to use that scratch path. It didn't: `pinchos config-path` still printed the real invoking user's actual `~/.config/pinchos/pinchos.toml`. `NSHomeDirectory()` resolves the current user's home directory from the account database (`getpwuid`), not from the `HOME` environment variable, so overriding `HOME` alone has no effect on `ConfigLocation`'s fallback branch. This is almost certainly fine in practice (a real Finder-launched process's `HOME` env var and account-database home directory agree for a normal user), but it means the correct way to test "default path when `XDG_CONFIG_HOME` is unset" - in this repo's existing subprocess-test style (see `SignalIntegrationTests.swift`) or manually - is to *omit* `XDG_CONFIG_HOME` from the child environment and compare against the *real* `NSHomeDirectory()`, not an overridden `HOME`. `Tests/pinchosTests/ConfigLocationDefaultPathTests.swift` does exactly that.
